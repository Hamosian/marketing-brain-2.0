# PART 1: DAILY DEMO REQUESTS REPORT

## Report title

Every run opens with: `## Daily demo requests report - [date]`. The date is the run date (today). The report covers all new contacts from HubSpot list 18323 since the last run.

## Run window and dedupe - the Outreach Log is the source of truth for "already processed"

`enterprise_form_submission_date` is a **date-only** HubSpot field. Filtering with an ISO timestamp (`>= 2026-06-03T06:31:34Z`) silently rounds forward to the next midnight and drops every contact from the partial day. Always pass dates as `YYYY-MM-DD`, never a timestamp. Do NOT use the Run Log timestamp as a filter - it is diagnostic metadata only.

**Cadence: morning Sun-Fri, evening ~5pm local Mon-Thu.** There is no Sunday evening run. The Sunday morning run clears the weekend backlog, and what arrives across the rest of a Sunday is too thin to earn a second pass. Nothing is lost: Step 1's lookback floors at the last Run Date, so Monday morning picks up everything that landed after Sunday morning. The Outreach Log dedupe below makes multiple runs per day safe: each run only surfaces contacts not already logged, so the second run just picks up what came in since the first. Tag each run's sends with the `Run` column (`morning` / `evening`, PART 5) so the learning loop can compare engagement between the two runs. The 48h follow-up timer (Step 4.7) counts from email 1's **confirmed Gmail send timestamp**, not from a run and not from the `Date Sent` column as the drafting run wrote it (see Step 0a: a draft created on run day N is frequently not sent until N+1, so the drafting date overstates the elapsed time by a full day).

Daily-run logic:

1. **Pull the window.** Read the most recent Run Date from the Run Log. Compute lookback = `max(today - 7 days, last Run Date)`. Floor at the last Run Date with **NO `-1 day` margin** (a margin re-pulls the prior day's cohort and inflates counts). Pull every contact with `enterprise_form_submission_date >= lookback` (GTE, `YYYY-MM-DD`). First run / no Run Log: default to 7 days back and create the sheet.
   - **Secondary guard:** if a contact's `meeting_creation_date_cp__c` (or booking) predates the last Run Date, it was already covered - drop it from this run's stats and processing.
2. **Dedupe against the Outreach Log.** Load all emails from the `Outreach Log` sheet into a set. Skip any pulled contact whose `email` (lowercased, trimmed) is already in the log, **regardless of status**. The log is the dedupe key, not the timestamp.
3. **Run the full pipeline** on the remainder (Step 1.25 onward).
4. **Log completeness - the anti-double-processing rule (hard rule per Nir, 2026-07-22).** After presenting, append an Outreach Log row for **EVERY contact this run surfaced - `Booked`, `Disqualified`, `Dropped`/filtered, drafted (`Sent`), and `Awaiting routing` - each with its status.** A contact logged once, under any status, is never surfaced again. This is the fix for the returning double-processing bug: previously `Booked` and filtered contacts were left out of the log, so they resurfaced on later runs (a contact reappearing on consecutive days, e.g. a filtered lead re-listed the next day, and yesterday's booked cohort re-counted as "today's" submissions). `Booked` / `Dropped` / `Awaiting routing` rows are **excluded from outreach-rate math** (only `Sent` / `Replied` count toward booking/reply rate) but are essential for dedupe. Then append the Run Log row (ISO timestamp + highest contact ID processed).

Dedupe-by-log heals weekend gaps, missed runs, late-arriving records, and date-rounding bugs automatically - **but only because every surfaced contact is logged (step 4).** If a run cannot write to the log (e.g. a read-only manual run, or a run that can't reach the live log), it MUST say so in the report: its dedupe is incomplete and it may re-show contacts a prior run already handled. The 7-day window is just a performance cap.

**Scope is the outreach subject patterns and the no-show and LHO sweeps, and nothing wider (hard rule per Nir, 2026-09-17).** This is a reply sweep, not an inbox review. Never run a general `is:unread` or catch-all inbox query, and when Nir asks "did you go over my inbox", the answer is the scoped sweep and what it found, not a wider scan. The 2026-09-17 run widened to the whole inbox, surfaced 17 unrelated threads, and buried the two replies that mattered.

Run before processing new leads. **Search windows follow the Evening run scope rule (Step 5): morning uses the full trailing windows below; evening scopes every search to messages since the morning run (`newer_than:1d`).**

**Read every thread with `get_thread`, never from a `search_threads` message list.** `search_threads` returns a truncated per-thread message list that routinely omits the most recent Sent message. Use it to FIND candidate threads, then call `get_thread` on each before judging whether a send went out or a reply is still outstanding. Skipping this produces both halves of the same error: re-drafting an answer Nir already sent, and demoting a row that was in fact sent.

**Then answer the LAST message in the thread, and nothing earlier (hard rule per Nir).** After `get_thread`, sort the messages by date and look only at the final one to decide what this reply owes. The truncated list makes an older question look unanswered, so the draft re-answers something Nir already handled hours ago, which reads to the lead like nobody is reading their email. Three consequences:

- **Last message is outbound (Nir or an AE) → the thread is closed.** Do not draft. Log only.
- **Last message is inbound but carries no question** ("thanks so much, you've been so helpful", a 🙏, "great, appreciate it") → the thread is closed too. Draft at most one warm line: thank them, wish them well with their show, stop. No product content, no re-answering, no links, no booking CTA, no closer question. Re-opening a resolved thread to re-explain something is the failure this rule exists to prevent.
- **Last message is inbound with a live question → answer that question only.** Earlier messages are context for what their words mean, never a second checklist of things to cover. If `get_thread` shows Nir already answered a question, it is answered, however recently.

If the thread's own `get_thread` output cannot be read in full (oversized output), extract every message's date, sender, and body with `jq`/python before drafting. Never fall back to the search snippet.

1. **Confirm sends.** Search Gmail Sent (last 24h) for the outreach subject patterns: `"Saw your Riverside request"`, `"Quick one about your Riverside"`, `"One more on your Riverside request"`, `"Re: your Riverside meeting"`, `"Fair point on the Riverside form"`, `"About your Riverside request on G2"`. ## Step 1.25: Validate each contact is actually a demo request

`enterprise_form_submission_date` alone does NOT confirm a demo request. Check `recent_conversion_event_name`:

**KEEP:**
- Event starts with "Interested In a Business Plan? Book A Demo Today | Riverside:" or otherwise clearly indicates a demo form completion ("Book A Demo", "Business Plan ... Redesign", "Business Plan 202503 - Product DEV", etc.).
- Event starts with `Riverside | <campaign name>: Business Plan ...` - a UTM-tagged version of the demo form. The `Riverside |` prefix is a marketing-source tag, not a webinar indicator; if the suffix after the colon contains "Business Plan" or matches demo-form patterns, treat as a real demo submission.

**DROP SILENTLY** (do not count, do not list anywhere):
- Event starts with "Typeform (ID:" - different channel.
- Clearly a webinar/workshop with no "Business Plan" suffix ("Webinar:", "Workshop:" prefix, or `Riverside | <event>:` where the suffix is NOT a demo-form pattern). When ambiguous, KEEP and verify via `form_comment`/content fields - false-positive webinar filtering loses real leads.
- "Meetings Link:" - already booked.
- Newsletter signup ("Newsletter LP:").

**In-product demo requests** - events like "Riverside Studio:" or "Riverside Studio | <user>'s Studio:" (typically the "Talk to sales" entry inside the product): treat ALL as legitimate demo requests. Do NOT silently drop on the basis that a studio session bumped the date. In any commentary, call these "demo requests from the product" - never "studio sessions" or "studio noise."

**The form asks different questions of different submitters - empty content fields are NOT a missing form fill.** `content_audience_dropdown`, `content_audience_specify`, and `content_goal_dropdown` are only asked on the low-intent branch (personal email and/or 1 license). A business-domain submitter, and anyone asking for 2+ licenses, is never shown those questions, so their absence is expected form behaviour and carries zero signal. NEVER treat empty content fields as evidence against a real demo request. `please_select_company_size` never populates on any contact: don't gate on it, and don't use it as the company-size fallback (use the associated company record's `numberofemployees`, else `how_many_accounts_do_you_need_` as a proxy, else "size unknown").

Decision tree for in-product demo events (still apply ownership/Filtered-Out rules downstream):
- **KEEP + draft** whenever the contact has a real company name (not blank, "NA", or the person's own name) OR a buyer-signal job title (CEO, Founder, Head of, Director, VP, Manager, Principal, Producer, Marketing, L&D, Artist at a real org, etc.). In-product demo requests are real: draft a standard Business reachout, acknowledge whatever signal you have, let Nir decide on send. There is no "Borderline - verify" bucket. A business-domain email with every form field empty still gets drafted; so does an existing paying self-serve customer with no form fields.
- **Extra confidence, not a requirement:** any of `form_comment`, `content_goal_dropdown`, `how_many_accounts_do_you_need_`; an open deal in an AE-routed stage ("Action Required" / "Marketing Qualified Lead" / similar); `business_trial_started=true` with `business_trial_start_date` matching the form date; or `num_associated_deals >= 1` with `hubspot_owner_id` recently assigned alongside the new form. Use these to sharpen the draft's hook. Their absence never downgrades the lead. (Owner auto-assignment, a lead-started trial, and an "Action Required" deal are all buyer signals or AE-flagging-FOR-Nir, NOT "AE already in motion.")
- **DROP SILENTLY** only when there is no usable identity at all: personal email AND company blank/"NA"/the person's own name AND no buyer-signal title AND no `form_comment`.

**Pre-opps vs. open deals:** do NOT use `num_associated_deals >= 1` alone as proof of an open deal - HubSpot counts pre-opps in both `num_associated_deals` and `hs_num_associated_open_deals`. Compare `hs_num_associated_open_deals` against `number_of_associated_pre_opps`:
- `open_deals > pre_opps` → a real open deal.
- `open_deals <= pre_opps` → all "open deals" are pre-opps (usually "Action Required" flagged for Nir). Treat as pre-opp, not an engaged deal. A pre-opp in "Action Required" = the AE flagging the lead FOR Nir's outreach → DRAFT, don't skip.

**Internal, test, and fake records - exclude from EVERY stat, but still list them in Filtered out.** Treat a contact as non-real when any of these holds: the email is `@riverside.fm` / `@riverside.com` (including `+alias` variants); `firstname`, `lastname`, `jobtitle`, or `form_comment` is literally "test"; `form_comment` is nothing but the submitter's own email address (a QA form-fill tell); the record is a Riverside employee testing under an external (non-`@riverside`) address, signalled by a matching `@riverside.fm` `+<name>` alias record in the same window that carries the same person's name (e.g. a `+matan` alias alongside a "Matan" submitting from an external domain); or lorem-ipsum / gibberish fills two or more of `jobtitle`, `form_comment`, HDYHAU; or the address is a **randomized local part on a shell domain** (e.g. `sayip36500@mapsguy.com`: a name-plus-digits mash the person would never choose, on a domain whose company record is a bare stub with no name, headcount or industry) **and** the record carries no job title, no company and no form comment. That combination is a QA or throwaway signup, not a lead (per Nir, 2026-09-02). Drop it, do not draft. Judge the whole pattern, not the domain alone: a real small company can have an unfamiliar domain, but it will have a name on the company record or something in the form.
  - **The throwaway drop does NOT fire on a lead from a market we sell Business into who asked for 2+ licences (hard rule per Nir, 2026-09-14).** Country plus a real licence count outranks an unfamiliar address every time: draft the standard Business reachout and let Nir decide on send. ### Step 4.5: Filter out low-quality leads

**Opt-out and deliverability - HARD filter, before every other rule:** if ANY of `hs_email_optout=true`, `unsubscribed_from_all_email=true`, `hs_email_bad_address=true`, `hs_email_quarantined=true`, `hs_email_bounce >= 1`, surface in Filtered Out with reason `Opted out of emails` (or `Bad address` / `Quarantined` / `Bounced address`) and do NOT draft. **Always pull and check `hs_email_bounce`: a bounced address routinely leaves `hs_email_bad_address` and `hs_email_quarantined` empty, so checking only those two passes a dead address through as sendable.** A bounce is also the one deliverability reason Nir wants named to him rather than buried: say in the report that the address bounced and that nothing was sent, so he can decide whether to chase another address. Beats every other rule including the 2+ license override, product-question exception, DQ self-serve invite, and AE-engagement carve-outs.

**On a bounce, check the contact for a second address before giving up on the lead, then stop (hard rule per Nir, 2026-09-18).** A bounce kills the address, not the lead, and the record often already holds another one. Read `hs_additional_emails` and `work_email` on the contact. If either is populated, surface it in Filtered out with the bounced address, the alternate, and the one question of whether to re-send there: do NOT re-send on your own, because a bounce is a deliverability event and re-sending is Nir's call. If neither is populated, abort and leave it. Do not guess an address from the domain, do not look for one outside HubSpot, and do not draft anything. Draft to the alternate on his word, and tell him the flag needs clearing on the contact or the next run will filter the lead again. Never clear it yourself: it is a deliverability record, and a run that edits one is a run that can talk itself into sending to a dead address.

Two exceptions:

Applies to `hs_email_optout` ONLY, never `hs_email_bad_address`/`hs_email_quarantined` (deliverability, not consent - always filter). If the opt-out timestamp isn't readable, default to drafting. Place in "Ready for outreach" and flag it as Nir's call. Beaten by the 2+ license override below and by every true-DQ filter.
  - **A buyer-signal title at an employer with a known headcount above the solo line beats the licence-count leg (hard rule per Nir, 2026-09-07).** When the job title is a buyer signal (Head of, Director, VP, C-suite, Founder, Manager, Producer, Marketing, L&D) AND the associated company record gives a headcount above ~10, send the **standard Business reachout**, not the choice email, even at `how_many_accounts_do_you_need_` = 1. The guard needs a **known** headcount, same as its buyer-signal twin; an empty `numberofemployees` leaves the licence-count leg intact. Filed on a 65-person Austrian telco whose blank title put a full Pro-versus-Business argument, a price step and a trial link in front of someone who had told us nothing at all.
  - **A colleague cross-reference beats the licence-count leg too (hard rule per Nir, 2026-09-14).** When the Step 4.1 same-company rule is naming a colleague at this lead's own employer, the buying team is demonstrably not solo: someone at that company asked for a team. So `how_many_accounts_do_you_need_` = 1 on this lead's form does not fire the solo-shaped leg, and they take whatever template the colleague's signal earns. Without this, the two rules contradict each other in the same inbox: the run tells one person Business is built for teams and names a price step, while telling their named colleague at the same 44-person employer to book a Business demo. Whichever of them forwards the email first sees both. The guard needs an actual cross-reference in the body, not merely a second contact somewhere in the file.
  - **The employer beats a sole-trader-sounding title. A media or production company is never solo-shaped (hard rule per Nir).** When the associated company is a production company, studio, agency, or media house (industry `ENTERTAINMENT` / `MEDIA_PRODUCTION` / `BROADCAST_MEDIA`, or a name or description saying it produces audiovisual content) and headcount is above the solo line, send the standard Business reachout even when the job title reads freelance, independent, or sole trader ("auto-entreprise", "freelance", "indépendant", "self-employed", "sole trader"). Those words describe how the person is contracted, not the size of the operation buying. A director or editor working inside a thirty-person production house is exactly our buyer, and routing them down to a trial argues our best-fit segment out of the deal. Anchor per the agency / production-company rule in PART 3 (separate productions), not the choice email.
- **2+ license override:** `how_many_accounts_do_you_need_` is 2+ ("2-5", "6-10", "11+") → ALWAYS draft a **Business reachout with the booking link**, regardless of status (including DQ), personal email, low-signal title, or catch-all email. Acknowledge the team-size signal in the body. Place in "Ready for outreach", NOT "Disqualified - self-serve invite". Use "Hi there" if firstname is malformed. Trumps the personal-email auto-filter, the standard DQ filter, and the DQ self-serve path. Does NOT override true-DQ filters (test records, Pakistan, internal emails, fake entries) and does NOT override a student or intern signal, which is always a DQ (see the student rule above). **EXCEPT:** a 2+ licenses lead whose `form_comment` is a pricing/quote request routes via the regional Slack DM (Step 4.2 pricing rule), NOT a booking-link email. And opt-out beats it. **Headcount guard: the override does not fire at 10 or fewer known employees (per Nir, 2026-09-02).** When the associated company record gives a headcount and it is <= 10, send the **choice email** instead and place it in "Ready for outreach" flagged as Nir's call. The choice email carries both the price signal and somewhere to go. Unlike the headcount guard this one may fire on an empty `numberofemployees`, because the trigger is the lead's country, sector or plan, all of which the record positively states. The licence count still says write to a team and still puts Business in the email; it stops choosing the template on its own.
- **Fake/spam pattern (true-DQ, filter even with 2+ license override):** filter when 3+ are true together: `company` identical to `jobtitle`; `form_comment` gibberish or a single nonsense word; personal email from a country where the company name matches no real org; `firstname`/`lastname` look fabricated (single-letter names, "School School"). List with `Fake-looking entry` reason.

### Step 4.5.5: Intent Read - infer the use case before drafting

Every lead that reaches drafting gets a one-line Intent Read that Step 4.6 and PART 3 consume. It exists for the common case, a blank form, and it replaces the old jump to the "Brands" fallback. Compute it from fields already in the Step 1 pull; it costs no extra calls. The data behind it is NEVER quoted back to the lead (no "saw you visited", no "since you've been recording"); the ONE exception is the lead's own account state (their plan, that they use Riverside), which the existing-customer templates already reference.

**Four slots:** `use_case` (podcast | webinar | video/clips | hosting/publishing | interviews | training | client-production | unknown) · `stage` (never-signed-up | fresh-visitor | active-user | power-user | dormant/cancelled) · `segment` (production-company | standard) · `confidence` (stated | inferred | guess).

**use_case - walk the ladder top-down, stop at the first hit:**

1. **Demo form (confidence = stated).** `form_comment` / `content_goal_dropdown` / `content_audience_specify` names it → use it, skip the rest. The form always wins.
2. **Prior meeting, Gong (confidence = stated, source `meeting`).** ONLY for leads with `number_of_meeting_records >= 1` that re-entered the pipeline (stale-meeting carve-out, no-show follow-up, churned customer). Pull the use case they discussed via `/gong-calls-explorer`. Never run Gong on leads without meeting history. Meeting content is partly AE-shaped (the lead may echo what was pitched), so it is tagged `meeting` in the log and its reply rate is judged separately by the learning loop.
3. **Signup onboarding answers (confidence = inferred, source `signup`).** `onboarding_questions_purposes` / `onboarding__what_do_you_want_to_create_with_riverside_` when 4 or fewer items are selected (webinars/virtual events → webinar; podcasts → podcast; executive/video interviews → interviews; internal communication → training; video marketing/talking head → video/clips). **More than 5 items selected is enthusiasm, not a use case:** it never picks the noun; it feeds the seriousness-axis altitude instead, and the noun comes from `onboarding_questions_intent` or the title. Then `onboarding_questions_intent`: Podcast → podcast; VideoClips/MarketingVideos → video/clips; LiveStream → webinar; CourseVideos → training; Transcription/skip → no signal. Backtested precision of this rung is ~60-65% (lower bound; the test population over-represents leads whose need changed), which is why the guards below and the Shape B guess-check exist.
4. **Current paid plan (confidence = inferred, source `plan`).** `customer_plan = webinar` with plan state = paid → webinar. Near-deterministic in backtest. `grow`/`pro` name no use case. Money beats the day-zero questionnaire, so this rung OVERRIDES rung 3 on conflict.
5. **Decisive product events (confidence = inferred, source `episodes`).** `lifetime_published_episodes >= 1` or `last_published_at` set → podcast + hosting/publishing. Rare (~3%) but decisive; also overrides rung 3 on conflict.
6. **Web entry page (confidence = inferred, source `web`).** `hs_analytics_first_url` (fallback `hs_analytics_last_url`), path only, ignoring dashboard/login/register/auth/start-actions: `/use-cases/<x>` → x; `/podcast-hosting` → hosting; `/blog/...` slug keywords (youtube, camera, podcast, webinar, interview) → that use case. `/pricing`, `/book-demo`, `/account/subscription` are STAGE signals (evaluating/upgrade-shaped), never a use case.
7. **Title (confidence = guess, source `title`).** The pain-map cluster routing in PART 3, unchanged. Nothing there either → `unknown`, source `brands`, and only then does the "Brands" fallback fire.

**Cross-rung guards:**
- **Stronger recent signal beats signup memory.** On conflict, rungs 4-5 beat rung 3 (a paying Webinar-plan customer gets webinars whatever they said at signup).
- **Production/agency segment reframes the noun.** When segment = production-company (industry ENTERTAINMENT / MEDIA_PRODUCTION / BROADCAST_MEDIA, or a studio/productions/agency/media-house name or description), the signup answer describes the person, not the buyer: "Podcast" from an agency producer becomes client production of podcasts. The agency/production cluster owns the angle.
- **The marketer blend.** Title in marketing/comms + signup VideoClips/MarketingVideos → don't bet one; write the marketing trio ("webinars, customer interviews, and the clips cut from the same recording").
- **Blend on conflict (2-3 slots).** When two rungs disagree and neither guard resolves it, name BOTH in the descriptive sentence, strongest first, using its existing 2-3 slot shape. A blend is always confidence = guess (Shape B). The backtest's misses were almost always between exactly two candidates, so naming both covers them.
- **Magic Clips never decides.** `used_magic_clips = true` only tilts the anchor toward clips/repurposing on whatever use case was otherwise chosen.

**stage - from plan + usage depth (picks the template, never from guessed data):** plan state = no plan record AND no usage fields → never-signed-up. Any other state, low `hs_analytics_num_page_views`, no/one recording → fresh-visitor. Recent `last_login_date`/`last_recording_date` with recordings or a studio → active-user (existing-user / self-serve-trial templates). Hundreds of page views plus heavy recordings/episodes → power-user (existing-customer framing; anchor on what their plan lacks). plan state = cancelled or `last_login_date` months stale → dormant/cancelled (win-back altitude, never "you just started").

**segment - the production binary only.** Production-company per the guard above → client work, multicam, post workflow. Everything else → standard: industry never touches the email (PART 3 "no industry framing" stands).

**confidence picks the email shape (PART 3 → Email shapes):** stated → Shape A (pain-led). inferred corroborated by a second rung → Shape A. inferred single-source or any blend or guess → Shape B (descriptive + the verbatim guess-check line).

**The template beats the shape rule when the template has no descriptive-guess slot (hard rule per Nir, 2026-09-01).** Shape B needs a role-anchored guess sentence for the guess-check to attach to. Several templates deliberately have none: the existing-customer and self-serve-trial templates open on the lead's own account state and go straight to the Business edge, which is a product fact and not a guess. On those, write the template and DROP the guess-check, exactly as self-review item 9 says. Do not bolt "Is that what you have in mind?" onto a definitive middle sentence to satisfy a confidence tag: it asks the lead to confirm a statement rather than correct a guess, which reads as a script. The Intent Read still logs its real confidence and source so the learning loop can judge the rung.

**Surface and log it.** One compact line per drafted lead in the report (`Intent: webinar · fresh-visitor · standard · inferred (signup)`), and write the `Intent` and `Intent Source` log columns (PART 5) on every Sent row so the learning loop can compare reply and booking rates by source. This ships unvalidated on the blank-form population (the backtest ground truth only covers leads who also wrote a comment), so the learning loop's Intent Source cut IS the validation: review after two weeks of runs and demote any source tag that clearly lags.

### Step 4.6: Draft emails

**Zeroth, read the Intent Read (Step 4.5.5).** It picks the use-case noun, the template (via stage), and the email shape. The pain-map cluster below picks the pain and the Business-edge anchor. They compose: the Intent Read says what the lead is making, the cluster says what hurts while making it.

**First, name the pain (one cluster only).** Before drafting, match the lead's `jobtitle` to a cluster in `pain-map.md` and read **that section only**. Pick the ONE pain whose signal actually appears in their `form_comment`, company, or licence count. Use its email insert as the personalized-context sentence, or reshape it. Full routing rules in PART 3 → "Adapting by role".

Three rules that override the map:

- **The form comment wins.** The map ranks what this cluster usually wants. It never overrides what this person wrote. When the comment names a pain, answer that pain and ignore the ranking.
- **A packaging question is not a pain to name.** The map's top finding is that most requesters are hitting a plan wall, not confessing a pain (feature moved behind Business, webinar cap, second seat). When that's the comment, answer it and get out of the way. Do NOT bolt a pain clause onto a "just let me upgrade" reply; it reads as deflection.
- **Never quote the map's verbatims to a lead.** They're other customers' words, recorded for internal calibration. Lifting one into an email is a confidentiality and credibility failure.
- **Do not shrink the pain to editing when the lead means the whole production (hard rule per Nir, 2026-09-02).** Several `pain-map.md` inserts name one leg of the job, and the Founder cluster's "still the one doing the edit" is the worst offender. A founder saying "scale through automation" is not describing an editing bottleneck. They are describing recording, editing, and publishing all landing on one person. Name the whole loop, because that is also what Riverside is: an end-to-end production studio, and shrinking the pain to post shrinks the product with it. Cleared shape: `Founders usually come to us when recording, editing, and publishing all land on the same person.` Use the map's narrower insert only when the lead's own words are narrow.
- **Never name the pain as a seat or billing problem (hard rule per Nir).** Several map inserts are phrased as cost consolidation ("when three editors are each paying for their own account", "when they're paying for two seats"). Do not send those. They fail twice: they assert a billing state you cannot verify from HubSpot, and they frame Business as a cheaper way to buy seats, which walks the lead straight to "then just sell me another seat." The map's own data says why this loses: "Need does not justify enterprise cost" is 47% of all losses. **Reframe every billing-shaped insert as tool fragmentation plus collaboration**: the team is producing content across three or four separate tools (record in one, edit in another, transcribe in a third), they want it centralised in one place, and they want to work on it together. That is Riverside's end-to-end production studio positioning and it is a value story, not a cost story. Example: `Content teams usually come to us when recording, editing, and transcription live in three different tools and nobody can work in the same place.`

If the title lands in the map's "Unclustered residual" or "Education / Academic" section, skip the map and draft from the form comment alone. Neither has a usable pain pattern.

Then draft per PART 3, then run the voice pipeline. **It runs on every prospect-facing body and every Slack handoff message, every run, no exceptions (hard rule per Nir, 2026-08-30):** `nik-voice` for voice, then the style pass against `drafting-style-digest.md` (in this skill's directory), then `de-ai` as the final pass. The style pass is Smart Brevity first (cut wordiness, buried lede, hedges, stacked front-clauses), then Provost rhythm (sentence-length variation, read-aloud test). **Running a script over the drafts is not this pipeline** and never reports as one: the self-review checklist below is the script, and it is blind to a buried lede, flat rhythm, or spec-sheet prose. The fact-check gate re-checks that this actually happened (its Step 3.6) and BLOCKS on `Voice: FAIL`, so skipping it here only moves the failure later. The digest IS the writing-optimizer pass for these emails - do NOT open the full references in `plugin-skills/writing-optimizer/references/` on a normal run; they are ~1,900 lines of methodology for one-paragraph emails. Escalate to the full `plugin-skills/writing-optimizer/references/smart-brevity.md` / `plugin-skills/writing-optimizer/references/gary-provost-rhythm.md` (or Made to Stick for a longer product answer that feels generic) only when a draft is still failing the digest's checks after two passes. Skip StoryBrand, JTBD, and Analogical Framing always (never right for 4-sentence emails). Keep it an internal critique → revise step, not a sub-agent spawn.

**The gate returns three severities and only BLOCK stops a draft (per Nir, 2026-09-07).** `BLOCK` (a CONTRADICTED claim with its source, a MISMATCHED fit, a named voice failure with the sentence quoted): fix and re-check. `CUT` (an UNVERIFIED claim that carries its search evidence): the clause comes out, the rest ships if it stands on its own, no redraft round. `FLAG` (a template or routing disagreement, a WEAK fit, a voice observation not on the named list, two of our files disagreeing, anything the gate is unsure of): ships as drafted, one bullet for Nir. A rule dispute is always a FLAG: the drafter's reading ships and Nir settles the rule. When the gate blocks on something that belongs in a lower tier, do not redraft; re-tag it and say so in the report. Full definitions in `demo-reply-fact-check` Step 4. Every block Nir overturns goes into `.claude/skills/demo-reply-fact-check/false-block-fixtures.md` the same day.

**Reporting the gate to Nir: short bullets, low-confidence items ONLY (hard rule per Nir).** The section exists so Nir can fact-check the fact-checker, so it must contain only the calls that could be wrong. Print bullets, never prose, never the per-claim table, never the sources.

Include a bullet only when the verdict is genuinely uncertain: a claim cut on thin or inferred evidence, a plan tier nobody could confirm, a source that was unreachable, a claim already sent to a lead that has no source in the KB. One line each, naming what is unverified and what it would take to settle it.

Exclude everything the gate is confident about. A claim contradicted outright by the pricing page or the help-center reference is settled, not a review item: fix the draft, fix the rule that produced it, and say nothing here. Same for anything that passed. Clutter is the failure mode, because the one line Nir actually needs to challenge gets lost in it. If every verdict was high-confidence, the section is one line: `Fact-check gate: passed, nothing uncertain.`

**The canonical order, and it is not negotiable (hard rule per Nir, 2026-08-31).** Every draft moves through these seven steps in this order, and no step may start before the one above it finishes:

1. Draft the body from the rules in PART 3.
2. `nik-voice`, invoked, not recalled.
3. The style pass against `drafting-style-digest.md`.
4. `de-ai`, invoked, as the final prose pass.
5. `critique`, invoked, scored inline on every body (SHIP or REVISE, two rounds max). It does NOT fold into the gate's Voice row.
6. The `demo-reply-fact-check` gate, as a separate `Agent` pass.
7. Only then write `drafts/YYYY-MM-DD-<run>.md` and present the report.

**"Invoked" means the `Skill` tool, in the drafting pass. Reading the SKILL.md file is not the pass (hard rule per Nir, 2026-09-28).** In the main run thread the `Skill` tool resolves `nik-voice`, `de-ai` and `critique` (confirmed 2026-09-28: `critique` loaded with its full body). The file-read fallback is only for a `Skill` call that actually failed or returned no body, and the pipeline line must then say so: `nik-voice ~ (Skill returned no body, read file)`. A file read with no failed `Skill` attempt before it is a ✗, never a ✓. The separate gate pass is different: inside an `Agent` pass the `Skill` tool hangs, so the gate reads files (its Step 3.6). The failure this closes: on 2026-09-28 the run read `nik-voice` and `de-ai` as files, never ran `critique`, ticked all three, and shipped "Grow does take a second editor." to a lead who had asked why she could not add one. The gate's Voice row passed it. Nir caught it, and it was the same miss he had flagged before.

**Critique checks the reply against the lead's literal question.** Put the lead's own words next to the draft when you score it. Two things fail `Point first` on sight: a lede the lead has to decode ("Grow does take a second editor" to someone who asked "is there a reason I can't do this?"), and a "why can't I" or "is there a reason" question answered without the reason or the known blockers. On a seat question the known blocker is the trial account, which is why the seat add-on template carries "One catch: a trial account can't invite an editor at all" - that clause ships in reply mode too.

**Steps 2 to 4 happen BEFORE the drafts file is written, never after.** The drafts file is the record of what Nir approved and what a later turn reads back, so a body that lands in it unpolished is the body that ships. This ordering has been the ambiguity: PART 6 says persist before presenting, Step 4.6 says polish before the gate, and neither said which came first, so a run could write the file and "polish" afterwards with nothing to show for it.

**A Skill call that returns only "Launching skill: X" did NOT load, and may not be ticked (hard rule, 2026-09-02).** The Skill tool sometimes returns the launch line with no skill body. When that happens the rules were never read, so applying them from recall is not the pass, and ticking it is a false claim in a file Nir approves from. Check every invocation for an actual body before you tick it. No body means re-invoke; still no body means mark it `~` with the reason and say so in the report. This happened to the `de-ai` call on the 2026-09-02 morning run: the tick went in the drafts file on a call that returned nothing, and only the fact-check gate's independent Voice check stood between that and unchecked prose reaching a lead.

**Name the skills you actually loaded, at the top of the drafts file.** One line: `Pipeline: nik-voice ✓ (Skill) | drafting-style-digest ✓ | de-ai ✓ (Skill) | critique ✓ (Skill, N SHIP / M REVISE fixed) | fact-check gate ✓ (separate pass)`. A tick you cannot justify is a lie in a file Nir approves from. Mark anything that did not run with ✗ and the reason. This line is the only durable artifact that the pipeline ran, which is why it is required rather than nice to have.

**A missing gate BLOCKS the writes. It is not a footnote (hard rule per Nir, 2026-08-31).** When the `demo-reply-fact-check` pass cannot run, the run may still present the report so Nir sees the work, but it may **NOT** create Gmail drafts and may **NOT** send the Step 4.7 follow-ups. Say so in one line at the TOP of the report. The reason this rule exists: for weeks the gate's absence cost nothing, so it kept being skipped and reported as a caveat nobody had to act on. Making it stop the writes is what converts a note into a signal. Nir can always override and tell the run to build them anyway; what the run may not do is decide that for itself.

**Then run the fact-check gate. Blocking, no exceptions.** Invoke the `demo-reply-fact-check` skill over every drafted email body before the report is presented. **Run it as a separate `Agent` pass, not as a re-read by the pass that wrote the drafts**, and hand it the inputs its Step 0 requires: the draft, the lead's title/company/size, the lead's plan state, the lead's own words, the ledger, and the voice sources for its Step 3.6. An author grading their own framing is the failure this gate exists to catch. If the run cannot spawn a separate pass, say so in the report. It extracts each capability, plan-gating, limit, and negative claim, verifies it against the product knowledge base, and returns VERIFIED / UNVERIFIED / CONTRADICTED per claim. Anything not VERIFIED gets cut or replaced, and the replacement is re-checked. The gate also returns a separate `Fit:` row and a separate `Voice:` row, and **any one of the three can BLOCK on its own**, so an all-VERIFIED draft still fails if it reads like a machine assembled it. Its `.claude/skills/demo-reply-fact-check/verified-claims.md` ledger caches adjudicated claims for 90 days, so a normal daily run resolves most claims without any research. If the gate blocks a claim that a rule in THIS file told you to make, fix the rule here as well as the draft: otherwise the same wrong claim returns tomorrow.

### Step 4.7: 48-hour follow-up (email 2)

A single second touch to leads we want to book. Not a sequence: one follow-up, then stop. **Morning run only - the evening run skips this step entirely** (Evening run scope, Step 5).

**Who is eligible.** A log row with status `Sent`, `Touch` = 1, whose email 1 was a Business booking-push (the standard "grab time [here]" outreach), and whose email 1 **actually went out at least 48 real hours ago**.

**G2 exception.** A G2 qualifier email (Step 1.1, free-email G2 lead) is also eligible, on the same schedule and the same auto-send trigger, but it gets its own reminder: no booking link, because the lead has not been qualified yet. Subject `Quick one about your Riverside request`, as a new thread. Body, adapted only in wording: `Hi [First Name],` then `Just wanted to follow up on your G2 request. If you can share what you're planning to record and how many people would use it, I'll point you to the right next step.` then `Nir`. Every suppression rule below still applies.

**Measure the 48 hours from the confirmed Gmail send timestamp. Never from the `Date Sent` column as the drafting run wrote it (hard rule per Nir).** This is the one check that has actually gone wrong. The log's `Date Sent` is stamped on the run that drafted the email, and Nir sends after he reviews, so a row can read `Date Sent` two days ago while the email itself left the building yesterday morning. Counting business days off the drafting date then fires a nudge roughly 24 hours after email 1, which is exactly what Nir does not want: a follow-up must feel like a considered second touch, not a next-day chase.

Concretely, before drafting any email 2:
1. Read email 1's real send timestamp: the `EMAIL 1 CONFIRMED SENT <timestamp>` note that Step 0a writes, or `get_thread` on the email 1 thread.
2. **No confirmed send timestamp means NOT eligible.** Do not infer one from `Date Sent`, and do not assume the drafting run's date. An unconfirmed row is a draft Nir has not sent yet, so there is nothing to follow up.
3. **Due on the second morning run after the send day, and never before.** Email 1 sent Monday morning is followed up Wednesday morning. Do NOT hold a follow-up an extra day just because the morning run fires a few hours short of a literal 48.00 hours: both runs are in the morning, so a strict clock would push every follow-up to day three and keep slipping. The binding constraint is the one Nir stated: a follow-up must never land the day after email 1. The second morning satisfies that; the first does not.
   - **The business-day guard removes weekend LANDING days. It does not remove weekend runs from the count, and it never adds a day.** Weekend mornings cannot be a due date, because the lead has had no working day to reply. When the second morning after the send day falls on a Saturday or Sunday, roll forward to the next weekday morning. Never roll forward past that.
   - An email 1 sent in the evening counts its send day as day zero, same as a morning send.

# PART 3: EMAIL DRAFTING RULES

Apply to ALL emails, daily batch or single reply.

## Structure (always one short paragraph + sign-off)

```
Hi [First Name],

[1-2 sentences personalized context] [1-2 sentences moving forward] If you want a walkthrough you can grab time [here](https://riverside.chilipiper.com/concierge-router/link/sdr-router?id=<EMAIL%20encoded>&meeting_source_cp=ai_sdr&meeting_campaign_cp=qbd_hs&utm_medium=email_nir), or is there a specific question I can help with?

Nir
```

One paragraph. No bullets, no feature lists, no P.S., no multi-section emails. The booking link is INLINE on the word "here" as a markdown link (Gmail draft creation converts it to `<a>`); never a separate "Booking link:" block.

**Recipients block sits above the body, only when there are multiple recipients:**
```
To: primary@example.com
Cc: secondary@example.com, work@example.com
```
Omit the To/Cc block if there's only a single address.

## Hard rules (canonical - every rule stated once here)

- **Keep the body short and coherent.** One clean idea per sentence. Don't stack clauses into a run-on (e.g. "you've been on the Webinar plan for a while, so there's a good amount on the Business plan that isn't in the self-serve experience once a few people are recording"). Cut to opener + one use-case sentence + CTA. If a Business nod is genuinely needed, keep it to one short clause. Read the middle sentence aloud: if it needs a breath mid-sentence, split it or cut it.
- **Never state the licence count back to them.** No "With 50+ people needing access…", "with 6 to 10 people needing access…", "you flagged 2-5 licences…", in any position. They filled the field; repeating it tells them nothing and burns the sentence. This is the ONLY thing the 2+ licence override means by "acknowledge the team-size signal": let the count decide that you write to a team rather than a solo creator, and that you pitch Business. Never put the number in the body.
- **The role-anchored noun must be a real category, never a lift of their job-title string.** Use "Content teams", "Marketing teams", "Producers", "Production teams", "Instructional design teams". A title like "Sports Original Content" becomes "Content teams", not "Original content teams" - pasting the title into the noun slot reads like a mail-merge.
- **No use-case signal at all? Say "Brands".** When there's no `form_comment`, no content fields, no completed signup-onboarding answer, and no product activity to infer from, the generic role noun ("Teams usually use Riverside for…") is empty filler. Write "Brands usually use Riverside for…" instead. Check the onboarding answers and what they've actually done in the product before falling back to it. **For a qualified lead with a blank form, run light enrichment first**: check the company's website/domain to infer the likely use case, and use it only to choose the angle. Never quote enrichment back and never mention anything you couldn't know from the form. Only if enrichment yields nothing usable do you fall back to "Brands."
  - **A use case the lead stated on the form always wins. Weak POSITIONING of it is the failure, not the use case (hard rule per Nir).** When `content_goal_dropdown` / `content_audience_dropdown` / `content_audience_specify` name what they want (customer education, internal comms, training, client work), use it: they told us. What's banned is describing it dully. "record once, then cut it into shorter pieces", "internal updates", "training content" undersell an end-to-end production studio and give the lead no reason to book. **Express the stated use case through the main-use-case vocabulary** Riverside actually wins on: podcasts, webinars, customer interviews, and the clips and repurposing cut from the same recording. Shape: `Brands usually use Riverside for customer education: webinars and interviews recorded once, then repurposed into clips.` Only when the form says nothing at all do you fall back to the generic list: `Brands usually use Riverside for podcasts, customer interviews, and the social clips cut from the same recording.`
- **Every sentence must earn its place.** Acknowledging HDYHAU signals or form fields ("Saw the referral from X and the 2-5 license request") usually reads as forced personalization that adds zero information - cut it. The middle sentence should either (a) answer a question they asked, (b) reference something specific they wrote, or (c) describe how their role uses Riverside - not read back facts they already gave the form. Rule of thumb: if the sentence would still be true and useful with the personalization removed, cut the personalization.
- **Never open a reply to a complaint on a negative note (hard rule per Nir, 2026-08-31).** When the lead is frustrated, stuck, or venting, the first sentence is neutral and useful, never apologetic and never a restatement of how bad it is. Banned openings: "Sorry, that shouldn't be this hard", "Sorry you're having trouble", "That sounds frustrating", "Sorry about that", and every variant that leads on the problem instead of the fix. They already know it is not working. Apologising first tells them nothing, concedes the tone of the complaint, and delays the only thing they wrote in for. **Open on the fact that resolves it**: the capability is there, the plan does cover it, or here is where the setting actually lives. Then give the steps, then the caveat that would block it, then the route to support. Warmth is fine anywhere after the answer; it is never the lede.
- **Never appraise what the lead wrote. Answer it with value.** When you reference something from their form, do NOT grade, validate, or characterise their thinking. Banned: "which is a fair way to approach it", "that's a smart way to think about it", "you're right to look at it that way", "makes sense", "good question", and every variant that scores their approach instead of advancing it. It reads condescending from a vendor, and it burns the one sentence that should have been doing work. Replace the appraisal with what Riverside would actually show them, phrased as something we want to do: "We'd love to show you how the Business plan could enhance the content and programming you're already running." Rule of thumb: if the sentence evaluates the lead, cut it and state the value instead.
- **An evident business does NOT get a Business pitch. Offer the walkthrough and stop (hard rule per Nir, 2026-09-09).** When the lead is plainly a company already, naming Business capabilities is arguing a case nobody asked for, and it is what makes these emails too long. Cut the Business-edge block entirely and end on the walkthrough CTA. The whole body is then: opener, one role-anchored use-case sentence, the guess-check if that sentence is a guess, CTA. That is the canonical Shape B example in this PART, and the Business-edge block was the bolt-on.
  - **Specify Business only when the lead raises it**: they ask what Business adds, ask which plan they need, name a capability they cannot find, or say they are comparing tiers. Then pick the anchor and the two trailing edges per the rule below.
  - **This does not touch the routing-down templates.** The choice email and the DQ self-serve invite still name Business, because there the point is to explain why the cheaper path fits. It also does not touch a lead who is genuinely evaluating Business off the back of a stated question.
  - Cleared shape: `Production teams usually use Riverside for podcasts, interviews, and the clips cut from the same recording. Is that what you have in mind? If you want a walkthrough you can grab time [here], or is there a specific question I can help with?`
- **Name a concrete Business-plan edge, not "there's a good amount on the Business plan."** This applies once the lead has raised Business per the rule above. Every such booking-push email must give one specific reason the demo is worth their time, drawn from what Business actually adds over self-serve. The verified Business-only list (source: the plan-tier breakdown in `references/product/help-center-reference.md`): the producer role and a producer running the session from backstage, async recording, team roles across owner/admin/director/editor, separate productions with per-production file naming and studio settings and directors/editors assigned per production, SSO and SCIM, the Business API, Salesforce integration, adjusting a guest's camera and mic during the session (guest input/output control), custom frame rates, XML/AAF timeline export, book-a-producer on demand, a dedicated CSM, priority support, SOC 2 report access under NDA, uploading a presentation file into the studio (slides upload / "Present slides", and handing slide control to a guest), uploading your own brand font, enforcing one brand default across all studios (brand-kit lock), **unlimited studios (and therefore unlimited shows and hosting)**, the **Marketo integration**, and the **AI Enhancements package** (AI Video Enhance, AI Color Correct, increased recording bitrate). Source for the last four: Ann Tsunakawa, B2B PMM, 2026-08-31.
    - **"Unlimited shows and hosting" is RESOLVED and usable, but name the studio (Ann Tsunakawa, 2026-08-31).** There is no cap on shows on any plan. The real gate is **studios**: every self-serve plan caps how many studios are included, and Business gives unlimited studios, which is what makes shows and hosting unlimited. So pitch "unlimited studios" and let shows follow from it. Never pitch "unlimited hosting" on its own to a Pro, Grow or Webinar customer: hosting is already on their plan and the claim reads as a vendor inventing a difference.
  - **Match the edge to the role with `business-edge-hooks.md` (in this skill's directory).** It maps the verified edges to four buyer motivations (team collaboration, production control, enterprise security, white-glove service), each with a pre-cleared benefit-led anchor line and two trailing edges. Read it to pick the anchor for a lead's role, and read its "do not ship" list before writing any security or integration edge: security certifications (SOC 2, ISO 27001, encryption) are company-wide posture, NOT a Pro-vs-Business gate, so never frame them as one; only Salesforce and the Business API are verified Business-gated integrations, not Marketo/HubSpot.
  - **Shape: one anchored edge, then two named without explanation.** Pick the ONE that best fits their use case, chosen from their `form_comment` first and their job title second, and give it a short clause of substance so they can picture it. Then name two more from the verified list as a bare list, no explanation, no benefit clause. The anchor earns the reply; the other two signal there's more without turning the email into a feature dump. Never explain all three, and never let the trailing two grow past a few words each. Shape: `What isn't in the self-serve experience is [anchor edge + short clause]. [Edge two] and [edge three] are on the Business plan too.` **Name Business in the trailing sentence, never a bare "are on there too".** When the anchor sentence ends on "the self-serve experience", "there" resolves to self-serve and the sentence tells the lead the trailing two are NOT gated, which is the opposite of the claim. Either name Business in the trailing sentence, or open the anchor with "On Business..." / "What Business adds is..." so the antecedent is already set.
    - **Pick the trailing two for the lead's stage, not for the ceiling (per Nir, 2026-09-02).** On a `fresh-visitor` or `never-signed-up` lead (Step 4.5.5), prefer capabilities they could use in week one: async recording, the producer role. Scale ceilings like unlimited studios name a limit they have never approached, and a cap argument is wasted on someone who has not made their first studio. Keep the ceilings for `power-user`, agency and production-company leads who are actually hitting them.
    - **The anchor clause states the benefit, not the feature's parts (per Nir).** Say what the team gets, not how the feature is built. Do NOT enumerate a feature's sub-components: for team roles, write "team collaboration" or "everyone records and edits in one shared account", never "owner, admin, director and editor". Do NOT write "instead of separate logins": Business members each sign in as themselves (SSO/SCIM, per-member roles), so that phrasing is contradicted. Do NOT reach for the billing contrast either ("one shared account instead of each person paying for their own"): it is banned by the billing-reframe rule in Step 4.6, and it asserts a billing state HubSpot cannot confirm.
      - **Bare shared-account access is CONTRADICTED at EVERY plan state, free included. This is a claim-level ban, not an audience rule (per Nir, 2026-09-02).** Never write that Business is what lets the team record and edit together. Editor add-on seats are buyable in-product on Pro, Grow and Webinar (see the seat add-on template in this PART), and the self-serve ceiling is one seat plus two Editor add-ons, so multi-person access is not the gate at all and below four people self-serve is the honest answer. What Business actually gates is **role-based team management across productions**, which holds at every seat count. Cleared wording, and it ships to a free lead exactly as written: `On Business your team works in one shared workspace, with roles controlling who can access which production.` **Never split the workspace half from the roles half**: the roles clause does the tier work, and "one shared workspace" alone is the contradicted shape. (A paying self-serve lead disproves the bare claim fastest, from their own settings page. That is why it gets caught, not why it is wrong.) Producer role → "you run the session from backstage without appearing on camera", not a list of controls. If the clause reads like a spec line, it's a feature; rewrite it as the outcome. The trailing two edges use the plain benefit noun too ("team collaboration", "the producer role", "async recording"), never a parts list.
  - **Branding is settled: never pitch it as one thing, and pitch only the two Business slices.** The word covers six differently-gated capabilities, so "the Business plan adds your own branding" is CONTRADICTED. Placing an element (logo, background, brand colour, image or text overlay) is All plans. The saved reusable brand kit starts on Pro. **Business-only, and on the verified list above: uploading your own brand font, and enforcing one brand default across all studios (brand-kit lock).** Studio lobby branding is Webinar + Business; live-stream logo removal is Grow, Webinar, Business; the export watermark clears at Pro. Lower thirds are **all plans** (Ann Tsunakawa, 2026-08-31), so answer a lower-thirds question freely and never pitch them as a Business edge. Full ladder and sources in `business-edge-hooks.md` and the branding entries in the fact-check ledger. **Do not re-derive branding gating from the plan-tier table in `references/product/help-center-reference.md`: it enumerates overlays only, never fonts or brand defaults, and reads as complete when it is not.** Same discipline for any capability not named above, in the anchor slot or the two short mentions: if it is not in the verified list, run the Step 4.2 confidence gate before it goes in an email. A named edge the lead can disprove in one click costs more than a vague one. Vague gestures at "a good amount that isn't in the self-serve experience" are still a fail: they tell the lead nothing and give them no reason to book.
  - **This applies to current customers too, and matters most there.** An existing free, Pro, Grow or Webinar user already knows what Riverside does, so "you've seen the basics" is the setup, never the whole middle. Follow it immediately with the specific thing their plan doesn't have. Same for anyone mid-trial.
    - **Above ~200 employees, never state what their current self-serve plan already does (hard rule per Nir).** Write only about Business. Do NOT tell a large-company lead that a feature they asked about is already covered on Pro, Grow or Webinar, even when it is true and even when it answers their form comment: it argues them back down a tier, and at this size the self-serve plan was never the destination. Answer the intent through the Business capability instead (their teleprompter ask becomes "on Business a producer can drive the script and prompter during the session"). **The only exception is when the lead raises the comparison themselves** - they explicitly ask which plan has a feature, ask whether Pro is enough, or name their current tier as the benchmark. Naming a specific feature is NOT raising the comparison. Below ~200 employees the honest "you already have that on Pro" answer still applies, since a real self-serve fit should not be pushed to Business. **Education is carved out of this rule (per Nir, 2026-09-02): headcount counts the institution, not the buyer.** A school district, university or education authority can employ tens of thousands while the person on the form is one teacher with one licence and one classroom. So when a lead is education-affiliated (Step 4.5) and the education ladder lands them on rung 2, send the choice email with the price step and do NOT let the institution's headcount bar the Pro half. This resolves a collision the fact-check gate used to block on: rung 2 said choice email, the 200+ rule said Business only, and rung 2 wins for education. Outside education the 200+ rule stands unchanged.
  - **Agency and production-company leads anchor on multi-client management, NOT the producer role (hard rule per Nir, 2026-08-23).** The producer role is the right anchor for an in-house producer. For an agency or production company the dominant ask is collaboration plus running many clients out of one account: `pain-map.md` Agency Pain 1 (own studio per client, 22 of 118) and Pain 5 (licence model doesn't fit one shop serving many clients, 26 of 118) outweigh Pain 2 (producer access, 26 of 118) once combined, and they are what the lead actually writes about. Anchor on separate productions: `each client gets its own production, with its own file naming and studio settings, and you assign editors per production`. Trail with team roles and async recording.
    - **Anchor on separate productions. It is verified and Business-gated (2026-08-23).** Business organises work into **productions**, one per client or use case, each with its own file naming and studio settings, with directors and editors assigned per production. Source: `references/product/help-center-reference.md` CATEGORY 8 (Riverside for Business) - "Shared workspace with multiple production domains, a centralized dashboard, and role-based permissions", the Business studio section on productions, and the Member roles entry. Full entry in `.claude/skills/demo-reply-fact-check/verified-claims.md`. This is the strongest anchor available for the agency cluster and it answers Pain 1 head on.
      - **Two limits.** Say "file naming and studio settings", never "branding": placing a logo is All plans, so a per-production logo is not the gate and naming it re-opens the settled branding ladder. And never claim a *count* of productions, studios, or clients: no source states one, and "unlimited productions" is the same unsourced shape as the retired "unlimited shows and hosting" claim.
  - **Anchor the edge on their title.** A producer or show designer cares about the producer role and backstage control; a marketing or content lead cares about async recording and team roles across the org; an IT or ops buyer cares about SSO/SCIM, the Business API, and Salesforce. Match the anchor to the role you're writing to, pick the two short mentions from the same neighbourhood, and pair the whole thing with the peer bridge for that role rather than repeating the default opener. **A word the lead typed is not a licence to name an edge their role would never buy (hard rule per Nir, 2026-09-02).** Read the title and the use case together, decide who this person actually is, and pick all three edges for THAT buyer. The failure to avoid: a recruiter wrote "integrate in our interview process" and the draft answered "integrate" with the Business API, which is an IT and ops edge. A Talent Acquisition lead does not buy an API; they buy candidates recording on their own time and a hiring panel that can all get at the recordings. Surface the read in the report line (title plus use case plus who the buyer is) so the anchor choice is checkable. Same trap for any keyword match: "security" from a marketer, "API" from a producer, "SSO" from a founder.
- **Opener.** Include "I run growth and marketing operations here at Riverside". Default opener when even the Intent Read is empty: `"I run growth and marketing operations here at Riverside."` then 1-2 sentences of personalized context.
  - **Never open with "My name is Nir" (hard rule per Nir, 2026-09-15).** The signature already says who wrote it, so the self-introduction is the second time in one email and it costs the sharpest position in the body. Start on the role.
  - **"I thought I'd reach out directly" comes OUT whenever the subject line already says it (hard rule per Nir, 2026-09-15).** The default subject is "Saw your Riverside request, wanted to reach out", so on every first touch that uses it the body may NOT also say "and I thought I'd reach out directly": that is the same sentence twice, one line apart, and it is the exact duplication the subject-repeat rule below already bans. The subject does the job. Keep the reach-out line only when the subject does not carry it, which in practice means a reply-mode subject or a custom one. The role anchor is unconditional; the reach-out anchor is not, and this retires the earlier "both anchors stay every time" wording.
  - Don't repeat the subject line - the subject already says "Saw your Riverside request…", so don't also open with "Saw your business demo request come through" (says the same thing twice). Only lead with "Saw your X…" when X IS the personalized hook on a FIRST touch (e.g. "Saw your question about frame rate support").
- **Peer bridge - add a peer line the Intent Read picks (hard rule per Nir, 2026-09-14).** The opener keeps the role anchor, "I run growth and marketing operations here at Riverside", and then carries the peer line. It no longer hangs off a reach-out line: on the default subject that line is gone (see the opener rule above), and the peer line is what now does the work of explaining why this email came from a person. Add ONE honest peer line, chosen off the **Step 4.5.5 Intent Read, not off a form comment** - driving it off the comment is why the bridge used to almost never fire. Three rungs, stop at the first that fits:
  1. **We do it too - Intent Read use_case is webinar, podcast, or clips.** These three are what Riverside marketing genuinely does, so the claim is true and you make it. Sanctioned wording only: webinar → "we run a lot of our own webinars on it", podcast → "we produce our own shows on it", clips/social/repurposing → "my team lives in clips and repurposing all day". **Give it its own sentence, immediately after the role anchor (hard rule per Nir, 2026-09-15).** Do NOT join it with "since": as a subordinate clause it reads as a justification for emailing, and the peer claim is the part that should land. Standing on its own it is a statement about us, which is what earns the reply. Shape: `I run growth and marketing operations here at Riverside. We run a lot of our own webinars on it too.` Two sentences, and the second is short on purpose. This retires the earlier "since" construction; do not reintroduce it.
  2. **I hear your role every week - a real buyer title you would never claim to be (producer, agency, founder, ops, L&D, talent).** `I talk with producers every week` - the real-category noun the middle sentence uses, never the lead's job-title string. Never joined with "since" (talking with producers is not a reason to email THIS producer, so the "since" logic breaks).
     - **ALWAYS carry the use case and the guess-check in the same sentence. The bare line is too thin to stand alone (hard rule per Nir, 2026-09-15).** "I talk with producers every week." on its own says nothing the lead can act on or correct: it asserts Nir meets people and stops. The line earns its place only when it names what those people need, which is what gives the lead something to confirm or correct. Canonical shape, and it is now the rung-2 default rather than a conditional: `I run growth and marketing operations here at Riverside. I talk with producers every week, and most use Riverside for podcasts, customer interviews, and the clips cut from the same recording. Is that what you have in mind?` The use-case list comes from the Intent Read; only when the Intent Read bottomed out at rung 7 do you use the generic trio.
     - **Carve-out: an existing user with real recording history drops the use case and the guess-check, and KEEPS the peer line (hard rule per Nir, 2026-09-17).** When `stage` is `active-user` or `power-user` (Step 4.5.5), guessing the use case back at someone with a recording history reads as nobody having opened the record, and the guess-check asks them to confirm what they already do every week. Drop those two. **The peer line itself still ships, every time.** It is a statement about us, not a guess about them, so none of the reasoning above reaches it, and it is the only thing in the opener that sounds like a person rather than a form letter. Never drop the whole bridge: an opener cut back to the role anchor plus the template's familiarity line is the failure this rule now forbids, and it left two existing paying customers with an email that said nothing about Riverside at all. The guess-check is for correcting a guess about a stranger.
  3. **No title and no use case - the empty-signal fallback (Nir's own line, replaces the bare default opener).** `I talk with dozens of marketers and producers every week`. Better than nothing because a person is talking, and it carries the use-case guess in the same sentence.
     - **JOIN it to the use-case guess, exactly as rung 2 does. Never ship it as its own sentence followed by a separate "Brands usually use Riverside for" sentence (hard rule per Nir, 2026-09-22).** Two consecutive sentences that are both about Nir and neither about the lead is two throat-clears before anything the reader can act on, and it is the shape that makes these emails read scripted. It also leaves a seam the joint check (self-review item 17) has to catch after the fact. Canonical shape: `I run growth and marketing operations here at Riverside. I talk with dozens of marketers and producers every week, and most use Riverside for podcasts, customer interviews, and the clips cut from the same recording. Is that what you have in mind?` The joined clause replaces the standalone "Brands" sentence, so the role-noun check (item 12) is satisfied by "most" without the generic noun: "most of the people I actually talk with" is a concrete claim where "Brands" is a vague one. Rung 2 already worked this way and rung 3 was the only one still splitting them.
  - **Producers and agencies take rung 2, not rung 1.** "We produce our own shows on it" to someone who produces for a living reads as "our marketing team has a podcast" - thin. "I talk with producers every week" is true (this pipeline is exactly that) and lands harder: it says I've heard your problem, not I'm your peer. **Marketers are the one title that takes the full rung-1 peer claim, because Nir is one**; for a Growth/Marketing Ops/Demand Gen/SEO/Paid title he can go the literal match, "I run marketing ops here, so I've built the exact stack you're evaluating."
  - **A bridge line is a claim about us, so the fact-check gate cannot verify it.** Every bridge line must come from the sanctioned wording above; a new one is Nir's to approve before it ships. Never claim a title or function that isn't real (Nir does NOT "run the webinar program").
  - **Tag every bridge email `bridge` in the Variant column.** This is a live A/B deployed 2026-09-14: the learning loop compares reply and booking rate for `bridge` rows against the pre-bridge default opener, which is the control. See the learning-loop watch in Step 5.
- **HDYHAU can set the angle, only when it's real.** When `how_did_they_hear_about_us__enterprise_form_` names something concrete (a specific podcast, community, conference, or referral), let it pick the peer bridge or use-case angle. Boring/blocklist answers (Google, LinkedIn, search) never touch the email. It informs the angle only: never quote it back and never write "I saw you found us via X."
- **Read for the concern under the words, never echo them back (hard rule per Nir).** A lead's message is a symptom, not a spec. Before drafting, name the real thing they are worried about and answer THAT, even when they never said it outright. "Should I still take the tutoring?" is not a question about tutoring, it is "will the effort be wasted if the product changes." "I want a one-stop-shop" after a browser complaint is "will I actually get record-plus-edit in one place." Reusing the lead's own noun ("yes, do the tutoring", "our one-stop-shop") proves you skimmed and answers nothing. Restate their concern in your own terms, answer the underlying worry, and cut any sentence that only parrots a word they used.
- **Casual inbound reply: answer it, don't announce it.** When the lead has replied in an existing thread, especially in a short or informal way, drop the opener entirely: no "I run growth and marketing operations here at Riverside", and no "Saw your question about X" restatement of what they just wrote. They know what they asked. Open on the answer itself ("Yep, all four.", "Yes, that works on the Business plan."), then give the detail. Restating their question back at them reads like a ticket auto-reply; matching their register reads like a person. This applies to every reply-mode email, not only product questions.
- **"I run growth and marketing operations here at Riverside" placement - ONLY at the start.** It's the opener line: very first or second sentence after "Hi [Name]," - or omitted entirely if the opener is a "Saw your question about X" product hook. NEVER in the middle or end, never after a product answer, never as a mid-email reintroduction. If a product-question draft answers the question first, drop the line entirely (the signature already identifies Nir).
- **"here" hyperlink placement.** "here" in "here at Riverside" is PLAIN TEXT, never a link. The ONLY hyperlinked "here" is in "grab time [here]" at the end. Hard rule.
- **NO DEMO PROMISES - zero exceptions.** Nir does NOT do the demo; demos route via Chili Piper to an AE. Never imply Nir personally walks the lead through anything. Banned phrases include: "I can walk you through", "I'd love to show you", "let me give you a demo", "happy to walk through" (any form), "happy to dig into", "happy to show you", "I can show you" / "let me show you", "let me run through", "I'll walk you through", and any "happy to [demo/explain verb]" or "I [demo/explain verb]". Rule of thumb: if it sounds like Nir is offering to personally explain/show/walk through anything, it's banned. The body sentence is for context (describe the use case, state a product fact, name what teams do). The walkthrough offer lives ONLY in the CTA "If you want a walkthrough you can grab time [here]" - delivered by the AE. Good replacements: "Marketing teams usually use Riverside for [X].", "Interviews are exactly what we're built for.", "There's a good amount on the Business plan that isn't in the self-serve experience.", or skip the body intro and go straight to CTA.
- **NO UNVERIFIED CLAIMS.** Never invent stats about the customer base, setup time, user count, or capabilities. If it's not a fact from riverside-intel or product-details, don't say it.

## Self-review checklist (mechanical final checks; nik-voice / writing-optimizer / de-ai run separately)

**A scripted or regex check is NOT the voice pass, and never substitutes for one (hard rule per Nir, 2026-08-30).** Grepping for em dashes, the sign-off, the closer, a banned-phrase list and sentence length is this checklist, nothing more. It cannot see the failures that actually make a draft read like a machine: a lede buried under disclosures, every sentence the same length, one clean fact per sentence with a plan tag bolted on, a spec sheet where a reply to a person should be. Before any draft is presented, actually invoke `nik-voice`, then the `drafting-style-digest.md` pass, then `de-ai`, and write a real critique of the prose. If a run reports drafts as checked when only the script ran, it has misreported the work.

**First, before any other check:** run a literal string search for the em dash (U+2014) and en dash (U+2013) characters in the email body. Replace any with a colon, period, or split sentence. (Report section dividers may use `-`; the email body may not.)

Then verify the Hard-rules items that are easy to miss:
1. Sign-off is "Nir".
2. "here at Riverside" NOT linked; only "grab time here" linked.
3. Demo-promise check - no "I can walk you through" or any banned phrase.
4. Unverified-claims check - no invented stats.
5. "I run growth and marketing operations here at Riverside" appears at the START or not at all. On a reply to an existing thread, it should not appear at all, and the email must not open by restating the lead's own question back to them.
6. No Business-trial reference - search for "Business trial", "Business plan trial", "started a trial".
7. Subject line: no name, includes "Riverside", not transactional.
8. Use-case accuracy (no "events"); "Business plan" not "Business side"; no industry framing.
9. Guess-check closer: if the middle sentence is a role-anchored guess at the use case, include "Is that what you have in mind?" between it and the CTA (see below). Skip if the middle sentence is a definitive statement or product answer.
10. Appraisal check: no sentence grades or validates what the lead wrote ("a fair way to approach it", "smart way to think about it", "makes sense"). State the value instead.
11. **Licence-count check:** search the body for a seat/licence number ("50+", "6 to 10", "2-5"). If one appears, cut the clause.
12. **Role-noun check:** the role-anchored noun is a real category, not their job-title string. **"Brands" fires ONLY when the Intent Read bottomed out at rung 7 with `unknown` / source `brands`.** If it resolved on any higher rung, a signal exists, the generic noun is not empty filler, and "Brands" is a fail: use "Teams" or the real category. A run cannot both resolve a use case from the signup answer and claim there was no signal.
13. **Front-clause check:** no sentence opens with a form-fact clause ("With X people…", "You flagged…", "Since you selected…"). Start on the value.
14. **Business-edge check:** the email anchors on ONE concrete thing Business adds, matched to their comment or title, then names exactly two more with no explanation. All three must be on the verified Business-only list in Hard rules (producer role/backstage, async recording, team roles, SSO/SCIM, Business API, Salesforce, custom frame rates, XML/AAF export, book-a-producer, dedicated CSM, slides upload into the studio, custom brand font, cross-studio brand default). **The bare word "branding" fails this check** - logos, colours and overlays are All plans and the brand kit starts on Pro, so name the font or the cross-studio brand default instead, never "branding". Fails also if: the trailing two carry benefit clauses instead of bare names, more than three are named, or the middle reads "there's a good amount on the Business plan that isn't in the self-serve experience" and stops there. Applies to current self-serve customers too.
15. **Fact-check gate (blocking):** run the `demo-reply-fact-check` skill over every drafted email before the report is presented. Any claim it returns as `UNVERIFIED` or `CONTRADICTED` must be cut or replaced before the draft ships. See Step 4.6.
16. Style pass against `drafting-style-digest.md` (Smart Brevity + Gary Provost Rhythm, distilled). Check every draft sentence-by-sentence against the digest - its stacked-front-clause check is explicit, so a one-line gloss is no longer the fallback. Open the full references in `plugin-skills/writing-optimizer/references/` only per the Step 4.6 escalation rule.
17. **Joint check - read the seams, not the sentences (hard rule per Nir, 2026-09-21).** Take the first three sentences after the greeting and name, for each, what connects it to the one before: a pronoun, a repeated noun, a cause, a contrast, a continued subject. No connective is a seam, and two seams in a body of four sentences or fewer means redraft. Every other item on this checklist grades one sentence at a time, which is why a body of individually correct sentences can still read as stacked fragments and pass. The peer bridge is the usual cause: it is required to sit in its own sentence, so the sentence AFTER it has to do the joining, either by answering it or by carrying it forward. It may never restate it. `I run growth and marketing operations here at Riverside. We produce our own shows on it too. Podcasts are exactly what we're built for.` is three correct sentences, two of which say the same thing, and it is the shape this check exists to stop.

## When the descriptive sentence is a guess - end with "Is that what you have in mind?"

When the middle sentence is a *guess* at the use case (the "X usually use Riverside for Y, Z, and W" pattern, inferred from role because they left no form_comment), follow it with **"Is that what you have in mind?"** - placed right after the descriptive sentence, before the CTA. It gives the lead a chance to correct the guess; it does NOT replace the required closer.

**When a Business-edge sentence sits between the guess and the CTA, keep the line where it is and bridge into the edge with "If so," (per Nir, 2026-09-02).** Do NOT move the guess-check down against the CTA to close the gap: past the Business sentences "that" resolves to the product facts, so the line asks the lead to confirm what Riverside does instead of correcting a guess about them, which is not what it is for. The bridge branches on the question rather than talking over it. Shape: `[Descriptive guess.] Is that what you have in mind? If so, [anchor edge]. [Edge two] and [edge three] are on the Business plan too. [CTA]`

**Use that sentence verbatim. It is a fixed line, not a paraphrase slot (hard rule per Nir).** No variants: not "Is that what you're hitting?", not "Is that what you're after?", not "Does that sound right?". The improvised versions read like sales-speak and land outside Nir's voice. Nine words, exactly as written, or drop the guess-check entirely.

```
[Opener]. [Descriptive guess: "Advisors usually use Riverside for X, Y, and Z."] Is that what you have in mind? If you want a walkthrough you can grab time [here], or is there a specific question I can help with?
```

**Use it** whenever the middle sentence is a role-anchored generalization ("Founders usually…", "Content teams usually…", "Producers usually…", "Advisors usually…"). **Don't use it** when the middle sentence states a product fact or references something the lead explicitly wrote (e.g. "Oral histories are exactly what we're built for.", "Saw your question about frame rate support - [answer].", "You've been on the Webinar plan for a while…"). Don't stack three question marks in one email - keep the guess-check tight.

# PART 7: MAINTAINING THIS SKILL (read before you edit it)

This file states the **current rules**, not their history. When Nir gives new feedback, distill it into the rule; do not append the story. This is a hard convention, because ignoring it is exactly how this file bloated to 1000+ lines of duplicated, contradictory rules before.

**When you get new feedback, do this:**

1. **Find the rule it changes** and edit that rule in place. Do not add a new dated bullet next to the old one. If the feedback contradicts an existing rule, replace the old wording, don't stack a newer note on top of it.
2. **Extract the rule, drop the narrative.** "Cat Rotolo at Together AI was wrongly marked borderline on 2026-06-16" is not a rule. The rule is "in-product demo request + real company + buyer-signal title = draft." Write the rule. Delete the anecdote.
3. **Keep at most a one-clause parenthetical** when it disambiguates a boundary the rule can't state cleanly, e.g. `(a well-known-in-its-vertical law firm doesn't count as Tier-1)`. No names, no dates, no email/company/license details, no PII.
4. **Provenance lives in git, not here.** Who asked and when is in the commit history and PR. Do not encode it as `(2026-07-09 update per Nir)` tags in the operating text.
5. **Deduplicate.** If a rule already exists elsewhere (routing table, email hard-rules, self-review checklist), edit the one canonical copy and reference it. Never restate the same rule in three sections.

**Litmus test before saving an edit:** could a new reader follow this rule without knowing the story behind it? If yes, you've distilled correctly. If the text only makes sense as a war story, you haven't turned it into a rule yet.
